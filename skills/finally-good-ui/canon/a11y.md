# A11y

Scope: the measurable accessibility floor (WCAG 2.2 AA) every screen must clear before any aesthetic judgment. These cards are the rubric's hard gate; AAA criteria are marked advisory.

### a11y.contrast-minimums

```yaml
id: a11y.contrast-minimums
domain: a11y
principle: "Body text needs 4.5:1 against its background; large text (24px+, or 18.66px+ bold) needs 3:1; UI component boundaries, focus indicators, icons and chart marks that carry meaning need 3:1 against adjacent colours."
why: "Low contrast is the most common accessibility failure, and it hurts everyone in glare, on cheap screens or with ageing eyes, not only low-vision users."
sources: ["WCAG 2.2 SC 1.4.3 Contrast (Minimum)", "WCAG 2.2 SC 1.4.11 Non-text Contrast", "Apple HIG, Accessibility (color and contrast)"]
applies-when: "All text, placeholder text that conveys information, icons, input borders, focus rings, and chart marks, in both themes and all states (hover, selected, error)."
not-when: "Disabled controls and pure decoration, which WCAG exempts; they must still read as disabled."
decides: [tokens.color, component.input, component.button]
tensions: [personality.calm, color.accent-restraint]
asked-by: [interview.context.environment, interview.constraints.a11y]
checks:
  measured: "axe color-contrast rule plus probe computing ratio for every text node and every input/button border vs its adjacent background, at light and dark, in default and hover states."
  judged: "Does any meaningful element pass only because it is technically 'decorative' or 'disabled'?"
```

### a11y.target-size

```yaml
id: a11y.target-size
domain: a11y
principle: "Every pointer target is at least 24x24 CSS px or spaced so a 24px circle around it touches no other target (AA); on touch-first screens aim for 44x44. Never block pinch zoom, and keep input text at 16px+ so mobile browsers do not auto-zoom."
why: "Small, crowded targets cause mis-taps for users with tremor, large fingers or a moving bus; time to hit a target grows as it gets smaller and farther."
sources: ["WCAG 2.2 SC 2.5.8 Target Size (Minimum)", "WCAG 2.2 SC 2.5.5 Target Size (Enhanced, AAA)", "Apple HIG, 44x44 pt hit targets", "Yablonski, Laws of UX, Fitts's law"]
applies-when: "Buttons, icon buttons, links in lists, checkboxes, table row actions, close buttons."
not-when: "Inline links within a sentence (WCAG exception); the text itself must remain legible."
decides: [tokens.space, component.button, component.icon-button, component.table]
tensions: [data.tension-density-clarity, personality.dense-expert]
asked-by: [interview.context.device, interview.context.environment, interview.constraints.a11y]
checks:
  measured: "Probe: bounding box of every interactive element is 24x24 or larger (or passes the 24px spacing test); at 375px viewport primary controls are 44x44 or larger. check-static rules user-scalable-no and small-input-font."
  judged: "Try the densest screen on a phone with your thumb: which targets do you miss?"
```

### a11y.focus-visible

```yaml
id: a11y.focus-visible
domain: a11y
principle: "Show a clear focus indicator on every keyboard-focusable element via :focus-visible, never remove outlines without a replacement, and never let sticky headers or overlays hide the focused element. Aim for a 2px ring with offset, 3:1 against its surroundings."
why: "For keyboard and switch users the focus indicator is the cursor; if it vanishes they are navigating blind."
sources: ["WCAG 2.2 SC 2.4.7 Focus Visible", "WCAG 2.2 SC 2.4.11 Focus Not Obscured (Minimum)", "WCAG 2.2 SC 2.4.13 Focus Appearance (AAA, advisory)"]
applies-when: "Every interactive element and custom widget, including cards that act as links."
not-when: null
decides: [component.focus-ring, tokens.color]
tensions: [personality.calm, color.accent-restraint]
asked-by: []
checks:
  measured: "check-static rule outline-none-no-focus; probe tabs through the page and asserts each focused element's outline or box-shadow changes, the ring colour is 3:1 or better vs adjacent background, and the element is not covered by a fixed/sticky element."
  judged: "Tab through the main flow without a mouse: can you always see where you are at a glance?"
```

### a11y.semantic-first

```yaml
id: a11y.semantic-first
domain: a11y
principle: "Use the native element for the job (button, a, input, label, nav, main, h1-h6, table) before reaching for ARIA; give every image an alt (empty for decoration), every input a programmatic label, and keep heading levels in order."
why: "Native elements bring keyboard support, focus, roles and states for free; a clickable div must reimplement all of them and usually misses some."
sources: ["WCAG 2.2 SC 1.3.1 Info and Relationships", "WCAG 2.2 SC 4.1.2 Name, Role, Value", "Pickering, Inclusive Design Patterns", "W3C WAI-ARIA Authoring Practices Guide"]
applies-when: "All markup, including component library wrappers."
not-when: null
decides: [component.button, component.nav, component.input]
tensions: [usability.consistency-standards]
asked-by: []
checks:
  measured: "check-static rules div-onclick and img-no-alt; axe rules label, button-name, heading-order, landmark-one-main, region."
  judged: "Read the page with a screen reader's headings and landmarks list only: does it describe the page's structure?"
```

### a11y.keyboard-complete

```yaml
id: a11y.keyboard-complete
domain: a11y
principle: "Every task must be completable with the keyboard alone, in a focus order that follows the visual order: a skip link to main, Escape closes overlays, dialogs trap focus while open and return it to the trigger on close, and nothing traps focus permanently."
why: "Keyboard access underpins screen readers, switch devices and voice control, and power users rely on it too; one unreachable control blocks the whole flow."
sources: ["WCAG 2.2 SC 2.1.1 Keyboard", "WCAG 2.2 SC 2.1.2 No Keyboard Trap", "WCAG 2.2 SC 2.4.3 Focus Order", "W3C WAI-ARIA Authoring Practices Guide, Dialog (Modal) pattern"]
applies-when: "Every flow in the blueprint, especially menus, dialogs, comboboxes, drag-and-drop and custom widgets."
not-when: null
decides: [component.dialog, component.menu, component.combobox, blueprint.flows]
tensions: [personality.dense-expert]
asked-by: [interview.constraints.a11y]
checks:
  measured: "Probe flow walk via Tab/Shift+Tab/Enter/Escape: every interactive element is reachable; focus order matches DOM reading order; opening a dialog moves focus inside and closing returns it to the trigger; a skip link exists before the nav."
  judged: "Can a user finish the top task in the brief without touching the mouse, and does any drag or hover-only action lack a keyboard path?"
```
